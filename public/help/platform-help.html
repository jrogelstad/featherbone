Platform administration

Running a Featherbone installation: its organizations, who may sign in to what, the instances they reach, and the packages those instances carry.

How the platform fits together

Orientation

The manager and its instances#

Every Featherbone installation has the same shape. One manager database holds the registry of instances, the organizations, the people and the sessions. Any number of instance databases hold application data — one per customer environment, so production, test and a demo are three instances, not three installations.

The manager is never served as an application. Pointing a browser at it answers 404. It has no screens of its own, which is why platform administration is served from an address with no database in it at all.

Each database carries a one-row marker recording what it is (manager or instance), its schema version and its mode — dev, test or prod. The mode is what draws the coloured banner across the top of the page after sign-in, so an instance says for itself what it is and nobody edits production thinking it is test.

Lives in the managerLives in each instance
Organizations, identities, passwords, access grants, the instance registry, the audit log, sessions Application data, forms, workbooks, settings, feather authorizations, local user profiles

The division answers two different questions. The manager answers who are you, which organization do you belong to, and may you enter this database? An instance answers what may you do once you are inside? Authorization never leaves the instance; only identity and reachability sit above it.

Three tiers of authority#

Three distinct levels of administration, each with a different reach.

TierReachWhat it can do
Platform administratorEvery organization and every instance on the installation Create, close and administer organizations; build, template, deploy to and drop instances; appoint an organization's first administrator; take over when a customer's administrators are gone; set the settings the platform owns.
Organization administratorOne organization: its people and its instances Create, suspend and delete identities in that organization; set and reset their passwords; grant and revoke access to its instances; configure how the organization signs in.
Tenant super userOne instance Whatever authorization grants inside that database. It is unrestricted within its own database and grants nothing at all outside it.

A platform administrator is an identity in the manager carrying a flag. It is not a Postgres superuser, and it is not a super user in some particular database. That matters because the tier it replaces used to be whoever has the cluster password, which could not be audited, scoped or revoked. This one can.

The tiers nest: a platform administrator can do everything an organization administrator can. They do not overlap sideways — a tenant super user is powerful inside one database and invisible outside it.

Opening the platform console#

Go to the server's address with no database in the path and sign in. That is the picker. If your identity carries the platform administrator flag, the picker offers Administer the platform, which opens the console at /platform.

The console is the only screen that crosses organizations, and it is deliberately served where no database is named. It therefore runs with no instance of its own, which is why every action on it names what it acts on — there is no ambient "current database" to assume.

Authority is re-read from your identity on each request. It is never taken from the session. Revoke the flag and the next click is refused, without waiting for a sign-out.

What the console shows#

Two lists, stacked.

Organizations says what each one owns: how many instances, how many people, how many of those can administer it, and how it signs in. A row reading none under administrators is worth acting on — that organization has nobody who can manage its own people.

Every instance on this installation is the per-instance Instances screen with the organization boundary taken off: each database with its owner, its state, the connection it is reached through, and what module versions it carries.

Click a row to select it. The buttons along the toolbar enable for what that row allows, and a disabled one explains itself when you hover it. Right-clicking a row offers the same actions as a menu. The tick boxes in the instance list are a separate thing — they choose which instances a group deploy acts on.

Organizations

The model

An organization owns people and instances#

An organization is the customer. It owns its instances, its identities and its sign-in policy. Every instance belongs to exactly one organization, and every identity belongs to exactly one organization.

That ownership is what makes the middle tier possible. An organization administrator has complete authority over everyone in their organization precisely because nobody in it is shared with anyone else.

Why an identity belongs to one organization#

A username is unique within its organization, not across the installation. Two organizations may both have an admin, and they are two different people.

The useful consequence: one person has one password across every instance their organization owns. Somebody with access to acme_test and acme_prod signs in with the same credential for both, and an administrator's password reset is one act that takes effect on both at once.

The cost is real and worth stating. A consultant who works for two customers has two identities and two passwords. That is deliberate rather than an oversight: a shared identity would mean one customer's administrator had authority over an account another customer also relied on, and no arrangement of that is safe. Where the duplication is genuinely a problem, single sign-on removes it — the consultant authenticates once at their own provider and each organization's identity becomes a binding to that subject.

Day to day

Onboarding a new organization#

Three actions on the console, in order. Suppose a new customer, Herbalife Nutrition, has signed up.

  1. New organization. Name it, and say whether it signs in by password, by single sign-on, or by either. If you are not sure yet, choose password — it can be changed later, and single sign-on needs details from their IT department that you probably do not have on the first day.
  2. Appoint administrator. Give a username and a password. This makes the identity if no such name exists in that organization, marks it the organization's administrator, and grants it no instance.
  3. New instance. Build their first database from a template.

Then hand the administrator their credentials. Who in their company reaches which instance is their decision from that point, made on the Users screen inside an instance, not yours.

Step 2 granting nothing is intentional and is the part people find surprising. Appointing an administrator says who may decide access; it does not hand over access itself. If you want that administrator able to open the instance you are about to build, grant it to them after step 3 — or let them grant it to themselves, which is within their authority.

Appointing an administrator#

Select the organization and press Appoint administrator. If the username already exists in that organization, the existing identity is marked as administrator and keeps the password it already has. If it does not, the identity is made with the password you give.

An organization may have several administrators, and the console's Organizations list shows how many. More than one is the sensible arrangement: an organization with a single administrator who leaves is the situation that forces a platform administrator to intervene.

Closing an organization, and opening it again#

Closing an organization stops its identities signing in anywhere — the picker reads the organization as well as the identity, so there is no instance left for them to enter by another route.

It touches neither the instances nor the data in them. Nothing is deleted, nothing is dropped, and opening the organization again restores sign-in exactly as it was. It is the right action for a customer who has stopped paying, or an account under investigation, and the wrong one for a customer who has genuinely left — for that, close the organization and then deal with the instances deliberately.

When an organization's only administrator has left#

Sign-in is organization-scoped, so a platform administrator is never signed in to another organization's instance in the ordinary way. That rule would otherwise make this situation unrecoverable.

The Users screen inside an instance offers platform administrators an organization picker. Choose the organization, suspend the departed administrator, and appoint the replacement.

This is the power that replaced the cluster superuser, so every use of it is written to the audit log against the organization acted on — who did what, to whom, when, and on whose behalf. Use it, but expect the record to be read.

Signing in

Passwords

The picker#

A URL with a database in it signs in to that database, as it always has. A URL with no database — the server's own root — answers with the picker: sign in once against the manager, see the instances your grants reach, and open one.

The picker proves who you are and nothing more. Opening an instance is what proves access to that instance, because the grant is read again at the door. Two things follow. A sign-in that now reaches several instances cannot walk into one it was never granted. And revoking a grant shuts the door at the next entry, rather than whenever the session happens to expire.

An instance that is closed, or down for maintenance, is listed and marked rather than hidden. Somebody who was working in it yesterday is told why it will not open today, which is more useful than an instance that silently vanishes.

A username in two organizations#

Because usernames are unique per organization rather than globally, a name that exists in two organizations is ambiguous at the picker, where no database has yet named the organization. You are asked to type the organization and sign in again.

The picker will not offer a list of organizations to choose from, and will not try your password against each candidate. Both are deliberate. A list would tell an unauthenticated stranger where a given username exists, and trying each candidate would count a failed attempt against every one of them — so three wrong guesses would lock accounts belonging to people who were never involved.

Organizations that require a second factor#

An organization can require a second factor. Those identities can use the picker, but they are not signed in by it: the code is sent by the instance's own mail service, and the manager has no mail service of its own.

So the picker lists their instances, and opening one lands on that instance's own sign-in, which asks for the factor. Nothing is admitted on a half-proved identity — the picker holds no session for them in the meantime.

Single sign-on

What single sign-on changes#

An organization can sign in through an identity provider instead of, or as well as, a local password. Microsoft Entra ID — still called Azure AD almost everywhere — is the reference target, and any OpenID Connect provider works the same way.

The organization's sign-in setting decides what is allowed:

SettingEffect
passwordThe provider is ignored, even if one is configured.
ssoLocal passwords are refused. The password is not even checked — there is nothing to be learned from the answer, so nothing is given away by the refusal.
bothEither works. Useful while an organization is moving across.

At the picker, Sign in with single sign-on asks which organization and sends the browser on from there.

Setting up Microsoft Entra ID#

On the console, select the organization and press Single sign-on. You need three things from the customer's directory administrator, and they need one thing from you.

FieldFor Entra ID
Issuerhttps://login.microsoftonline.com/<directory>/v2.0 where <directory> is their tenant id
Client idThe application id of the app registration they create for Featherbone
Client secretA secret from that registration. It is stored encrypted and is never shown again — the form says New secret on a provider that already has one.
User name claimpreferred_username unless their directory is set up unusually
Administrator groupOptional. See below.

What they need from you is the redirect URI to register against that app registration: your server's address followed by /auth/sso/callback. If the server sits behind a proxy or load balancer that rewrites the host, set ssoCallbackUrl in config.json so the address you hand them is the public one rather than the one the server sees.

Then set the organization's sign-in to both and try it before setting it to sso. Moving straight to sso on an untested configuration leaves nobody in that organization able to sign in.

What happens the first time somebody arrives#

Who somebody is comes from the provider's subject, never from the email address. An address can be reassigned to a new employee; a subject at an issuer cannot. This is the single most important thing to understand about the federation, because it is what stops a departed employee's reissued mailbox inheriting their access.

The first time a subject arrives, one of three things happens.

  1. It is already linked to an identity here, and is that person.
  2. Its user name matches an identity that already exists in that organization, and the two are linked. This is the path for somebody who was here before the organization moved to single sign-on: they keep their account, their grants and their history.
  3. Neither, and an identity is made — but only if the provider is configured to make them. It is granted the databases the provider names and nothing else.

All three are written to the audit log. If the provider is not set to make accounts and somebody arrives who has none, they are refused with a message saying an administrator can create one. Leaving account-making off is the safer default for an organization whose directory contains more people than should have access.

The default grants are worth setting deliberately. An account made with no instances named reaches nothing until somebody grants it, which is safer than an account that reaches everything.

Administrator rights from a group claim#

Name a group in the provider's configuration and membership of it carries the organization-administrator flag.

It is applied on every sign-in, not only the first. So a group taken away in the directory is taken away here the next time that person signs in, without anyone remembering to do it by hand. That is the point of wiring it to the directory at all.

What a provider cannot decide#

A provider vouches for who somebody is. It does not decide whether they may come in.

  • A suspended or locked identity is refused whatever the provider says.
  • Platform administration is never a claim. A provider belongs to one organization, and that flag crosses all of them — a customer's directory cannot be allowed to mint authority over other customers.
  • A second factor requirement is satisfied by the provider's own policy, since it applied that policy before it vouched for anyone.

Instances

Building

What an instance is#

An instance is one application database, registered in the manager and served at /<database>/. It belongs to one organization and carries its own data, forms, workbooks, settings and authorizations.

Even a small customer usually wants more than one — production and test at least, often a demo as well. That is why there is no single-database mode.

Building one from a template#

Select the organization, press New instance, and choose a template. The build is a sequence of steps, each recorded as it completes: clone the template, verify the clone's marker, grant every administrator of that organization access with a tenant super user profile, and open it for sign-in.

Because each step is recorded in the manager, a build that stops partway resumes from where it left off rather than starting again, and two servers cannot both build the same instance. If you see an instance offering Resume, that is what it means: something interrupted the build and the remaining steps are still waiting.

A template is made by copying an existing instance — select it and press Template. The source must be quiet while the copy runs. This server lets go of its own connections to it automatically; connections from anywhere else, including another node or somebody's open psql, make the copy refuse rather than produce a torn clone.

Registering a database that already exists#

Registering does not build anything. It takes a database that already exists in the cluster and tells this installation to serve it.

The database must carry a marker saying it is a Featherbone instance; anything else is refused with the reason. To build a new database from scratch, use node install.js --instance <name>, which installs and registers it.

Attach is the related action for an instance that belongs to no organization at all, which is what an installation predating the organization model has. It puts an existing instance under an organization so its people can be granted access to it.

Running

Closing an instance#

Closing stops sign-in to one instance. The database is untouched and everything in it stays. Open it again and sign-in resumes.

You cannot close the instance you are signed in to from inside itself — a rule that exists to stop an administrator locking themselves out of the only screen that could undo it.

Maintenance#

Schema changes are not run under live traffic. An instance being deployed to is therefore held in maintenance first and let go afterwards, and Deploy does this bracketing for you.

While maintenance is on, the instance answers 503 with an explanation — not the 404 an unservable database used to give — for everything except its own pages, sign-in and the administration routes. Only a platform administrator can sign in. That exception matters on an installation with a single instance, because the screen that ends the maintenance is served from that instance.

The state can also be set by hand, which is what you want when something stopped halfway and you need the instance quiet while you look at it. Beginning and ending are both audited.

The state is a column on the registry row, so a manager database built before the column existed needs node install.js --manager run once. Until then the screen reports no instance in maintenance and the button says what to do, rather than failing — an upgrade is never blocked by it.

Dropping an instance#

Drop removes the database and its registration. It is audited, and it will not drop the instance you are signed in to.

There is no undo. The safety net is a backup taken beforehand, and nothing in the console takes one for you.

Demos

Demo instances and when they expire#

An instance marked as a demo carries an expiration date. Once that date passes, a sweep closes it: sign-ins stop, the data stays, and the close is audited. The server runs the sweep when the registry loads and every hour after, and the Instances screen can run it early.

Closing is immediate and reversible because somebody may yet ask for the instance back. Moving the expiration date forward is how they get it — reopening an instance whose expiration is still in the past only has it closed again on the next pass.

The grace period before a demo is dropped#

A demo is dropped once it has been expired for demoGraceDays, which is a month by default. Dropping is neither immediate nor reversible, which is exactly why it waits: the month is there so that somebody who notices their demo has gone quiet has time to say so.

When it goes, the database and its data go. The registry row stays, marked deleted, so the record of what was there and when it went outlives the instance.

Set demoGraceDays to 0 and an expired demo is only ever closed, never dropped. A config.json written before the setting existed has no such key, which reads the same as zero — so an installation being upgraded drops nothing until somebody adds the key deliberately.

Packages and upgrades

The two acts

Install puts files on a server#

Install registers a package's files on this server. It unpacks the package to a directory per version and records that the version exists. It changes no database at all.

node install.js --package <directory-or-tarball>   # [--force]
node install.js --packages                         # what is installed

One directory per version, deliberately, because two databases served by one process may run different versions of one module — test on 2.1 while production is still on 2.2. A version already installed is left alone unless --force says to replace it.

A package's own libraries are installed inside its own version directory, which is what lets two versions of a module depend on different releases of the same library.

The console cannot do this yet. Install is a command-line act, and the Deploy form can only offer packages this server already holds. If the package list is empty, nothing has been installed on this server.

Deploy applies a version to a database#

Deploy applies one installed version to one database: it creates or alters that database's tables, loads its workbooks and data, and records the version now deployed there.

It holds the instance in maintenance while it works, applies the package, and lets the instance go. The same act is available from the command line and from the screens, and it is audited at both ends.

node install.js --deploy <module>[@<version>] --instance <database>
node install.js --deploy <module>[@<version>] --manager

With more than one version installed the version must be named. Holding several at once is the point of the design, so the choice is never guessed.

The manager follows the same rules as any instance, with one practical difference: deploying to it takes the administration screens down while it runs, which is why a manager deployment is a command-line act rather than a button.

Deployments go forward only. There is no rollback, and restoring from a backup is the reverse — so confirm a restore point exists before you start, because "forward only" is only safe if the backup is real.

Reading the fleet

Which half a module is on#

A module runs from its package when this server holds that module at the version the database says it carries. Otherwise it runs from the database's own rows. It is decided per module and per database, so one instance can have some of each.

The rows are not deleted when a package takes over. They are the fallback for a module with no package, and the record of what a database carried before it was packaged. But they are no longer what runs, and they used to say nothing about it. Two things now do.

The rows refuse to be changed. Editing a module's client script or one of its service rows, for a module this server serves from a package, is refused with a message naming the module and version — because the save would appear to take and change nothing that runs. The refusal is by where the call came from, not by who made it: Install and Deploy write those rows as part of their work and are unaffected, while a person at the Develop workbook is refused. Including a super user, who is precisely the person who gets past every other check.

The screens say which. See the tags below.

Behind, adrift, and from rows#

The Instances screen and the platform console mark each instance. Hovering the count lists each module with its version.

TagMeansDo
N behindIt carries a version older than one this server holds.Deploy it.
N adriftIt names a version this server does not hold, so it has quietly fallen back to running the code in its own tables.Install the package, or deploy a version this server has.
N from rowsModules with no package on this server at all.Usually nothing — but see below.

Adrift is the one to care about. Nothing else tells you about it. It happens when a server is rebuilt without its packages, or when a second node was never installed to, and what it means in practice is that two nodes can be running different code for the same database.

From rows is ordinary for now. Core is always one of them: it is installed from the repository rather than as a package, so every instance reports it until that changes.

Upgrading

Upgrading a fleet#

Deploy from the Instances screen applies one package version to one instance. The console does the same across a group: tick the instances in Every instance on this installation, press Deploy, and choose the package.

A group is a sequence of single deployments, not a second way of deploying. Each instance is held, applied to, and let go in turn — so one is down at a time rather than all of them.

That is also why the instances are named rather than implied. Trying a version in a test database before production is the same action with one name in the list; an urgent patch across the fleet is the same action with several.

A fleet upgrade is a rolling outage. The screen tells you how many instances are behind and leaves the order to you, because the order is an operational judgement — which customer can be down, and when — and not something the software should decide.

When a deployment fails#

By default the first failure stops the rest. The instance that failed is left held in maintenance, and the instances after it in the list are not attempted. The answer tells you how many were deployed, which one failed, and how many were not tried.

Tick Carry on and the instances that can take the deployment get it, while the one that could not stays held for somebody to look at.

A failed deployment leaving the instance held is deliberate. The schema is then in a state nobody has checked, and ending the maintenance from the Instances screen is the deliberate act that says somebody has checked it. Both the group and each instance in it are audited.

Settings the platform owns

What they are

The edition#

A settings row is normally the instance's own: its super user may change it, and the instance's authorization can grant others the same.

Some settings are not the instance's to decide. The edition is the case this exists for. It says what an instance offers — which workbooks appear, and so what the customer has bought — which is the platform's to set and not the customer's, even though the customer's own administrator is super user inside their instance.

Making a setting the platform's#

A setting becomes the platform's in either of two ways.

  • Its definition says it is platform-only, which is how a module declares one of its own settings.
  • config.json's platformOnlySettings names it, which is how an installation locks a module's setting down without waiting for the module to declare it: 
    "platformOnlySettings": ["jobShopSettings"]

Changing one then needs a platform administrator — the flag on the identity in the manager, not the instance's super user — and anyone else is told whose it is.

Reading is unchanged. The platform decides who sets it, not who sees it. The framework's own internal saves, such as the feather catalog, are unaffected.

Why an edition is not a security boundary#

Worth being clear about, because it is easy to assume otherwise.

Every feather and every route is installed whatever the edition. So the edition decides what is offered, not what is possible. Treating it as a wall would mean shipping a separate package for each edition, which is exactly the proliferation it exists to avoid.

What is a boundary is who may change it. That is why the setting is locked to the platform tier, and that is the whole of the protection it provides.

Authority and the audit

How authority works

Authority is read, never remembered#

Every privileged act re-reads the flags on your identity from the manager. Nothing is trusted from the session, and nothing is cached for the length of one.

Two consequences. Revoking somebody's platform flag takes effect on their next click, not on their next sign-in. And entering an instance re-reads the grant at the door, so a revoked grant shuts that door immediately.

What is written to the audit#

The audit log lives in the manager and records who did what, to whom, when, and on whose behalf. Privileged acts are written to it as a matter of course:

  • Creating, closing and reopening an organization; appointing its administrators.
  • Creating, suspending and deleting identities; setting passwords; granting and revoking instances.
  • Making an identity on a first single sign-on arrival, linking an existing one to a provider, and granting or revoking the administrator flag from a group claim.
  • Building, templating, closing, deploying to and dropping an instance; beginning and ending maintenance; both the group and each instance of a fleet deploy.
  • Closing and dropping an expired demo.
  • Every break-glass act taken on a customer's behalf.

The recent privileged changes for an organization are shown on the Users screen inside its instances.

Running the installation

Capacity and addressing

The connection budget#

Each instance the server loads gets one connection pool for the whole process, plus one held connection listening for events. The worst case for one node is:

instances x (pgTenantPoolSize + 1) + pgMaxConnections

pgTenantPoolSize defaults to 10 and pgMaxConnections, which caps the manager's own pool, defaults to 10 as well. A quiet instance holds only its listener, so the practical floor is instances + pgMaxConnections.

One pool per database, not one per service. A dozen services each asking for their own pool would multiply that budget by twelve. Sharing is also what lets the server give a database up — releasing an instance before a template copy or a drop ends the pool everyone was using, rather than one service's and nobody else's.

Size max_connections on the cluster from the worst case across every node you run, with headroom. Lower pgTenantPoolSize or put PgBouncer in front when instances multiply.

Addresses the server answers itself#

Featherbone's URLs are shaped /<database>/..., so the first segment of a path normally names an instance. A few do not, because they belong to the server itself:

PathIs
/The picker: sign in, choose an instance
/my/instancesThe instances your grants reach
/auth/sso/*The single sign-on round trip. The callback is the address you register with the provider.
/platformThe platform console

So auth, my and platform are refused as instance names. An instance called platform would be shadowed by the console and could never be opened, so it is better refused at the point somebody tries to create it.

From the command line

Doing it without the console#

Some acts have no button, and some are better done from a shell. These are the ones worth knowing.

ToRun
Build or upgrade the managernode install.js --manager
Build an instance and register itnode install.js --instance <name> --organization "<name>"
Put a package on this servernode install.js --package <dir-or-tarball>
See what is installednode install.js --packages
Deploy to the managernode install.js --deploy <module>@<version> --manager

Installing an instance attaches it to the organization, creating that organization if it does not exist. It makes the service account from config.json an identity in that organization, grants it the instance, and appoints it the organization's administrator — and, when it is the first identity on the platform, the platform administrator. That is how the very first installation gets somebody who can sign in.

Re-running an install on an existing instance is safe. It updates the installed scripts and changes nothing in the manager it already made.
