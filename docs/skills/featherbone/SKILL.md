# Featherbone: project hub

Featherbone is a JavaScript persistence framework for object-relational database apps (Node + Postgres, Mithril client, GPLv3, essentially one maintainer: John Rogelstad). This skill is the map: what the pieces are, where the authoritative docs live, how John wants work done, and the traps that have already cost time. It deliberately does not copy the long plans; those are living docs and a copy would rot. Read the doc named for your task (section 3) before you act.

Featherbone is independent of the DCI web migration. Do not apply DCI conventions here and do not use the `dci-postgres` connector.

## 1. Architecture in one page

- **Feathers** are JSON class definitions that generate the schema. Every table inherits from an `object` base table (`_pk bigserial`, `id text UNIQUE`, `created`, `updated`, `is_deleted`, `lock`) via Postgres table inheritance. Each feather gets a generated read view `_<table>` plus insert/update/delete triggers.
- **Relation columns** are named `_<key>_<relation>_pk`. Views expand relations with correlated subqueries (to-one: scalar subselect; to-many: `ARRAY(SELECT ...)`). Consequences already measured: no indexes or FKs on relation columns, and view *planning* (75-150 ms) dominates execution (1-9 ms).
- **Natural keys** are meant to be unique but are only plain indexes; on inheritance hierarchies the index sits on the empty parent table only.
- **Authorization** is application logic: `$auth` rows plus `Role`/`RoleMembership`, checked in `tools.js`, `feathers.js`, `workbooks.js`. Membership is a recursive CTE (`tools.memberNames`), not `pg_has_role()`. Every real query runs as the instance's service account (`TenantService.pgUser`). Who a user *is* is an identity in the manager, never a Postgres login role (section 5).
- **Multi-tenant**: one Node server, one database and one `pg.Pool` per instance. The `Tenant`, `TenantService`, `Organization`, `Identity`, `AccessGrant` and `AdminAudit` feathers live in the **manager** database (`managerDatabase`, default `db_manager`), along with `$session`; `Edition`, `ServerProcess`, `Notice` and `SendMail` are Core. The manager is never routable (see section 5). An instance leaving the registry gives up its pool and LISTEN connection; `datasource.registeredTenants()` reports what the process is serving.
- **Modules** (SupplyChain, Job Shop, Admin Console, CronJob) are zip packages with a `manifest.json`, installed through the client's Develop workbook or the server's `/module/install` route. `installer.js` accepts only `install`, `execute`, `module`, `service`, `feather`, `batch`, `workbook`, `settings`; anything else rolls back with "Unknown type". Module client code (Design, Plan, Make, Bill ...) is stored in the database and run with `new Function`, not read from the repo.
- **Client**: Mithril 2, Pure CSS, statechart library (`client/state.js`), components registered in a catalog (`f.catalog()`), shared via `catalog.register("global", ...)`. Component files do not import each other; follow the catalog pattern. `index_debug.html` loads unbundled source and `config.json` has `debug: true`, which makes `server.js` serve it. `client/clientmin.js` is a bundle that is not regenerated: never edit it.
- **Lint** is JSLint (`client/jslint.mjs`); keep touched files clean. Docs are YUIDoc comments.
- Large files: `crud.js`, `datasource.js`, `server.js`, `client/components/table-widget.js` (2.5-3k lines each).
- Money columns use the `mono` type. Installing SupplyChain via `node install.js --dir` creates them as `json` (plan defect 0.11); install through `/module/install` instead.

### Tenancy and identity: where it landed (ADR 001)

Item 1.1 -- one tenant's admin could reset another tenant's user's password, because users were cluster-wide Postgres roles -- is **fixed and demonstrated**. Tier B of the tenant plan is closed (B.8, 2026-10-15): there is no role path and no `authStrategy`; what remains of 1.1 is John running the migration on each real installation.

The shape now in the code:

- **One mode.** Every installation is a **manager** database (`managerDatabase`, default `db_manager`) plus one or more **instances**. A database says which it is in `"$db"` (kind manager|instance, schema 2). The manager holds the registry (`Tenant`, `TenantService`), the identities and `$session`, and is **never routable** -- there is no URL for it, which is why administration runs inside an instance. `node install.js --manager` builds it; `node install.js --instance <name>` builds or upgrades an instance and registers it.
- **Sign-in is by identity, only.** scrypt verified in Node against `identity.password_hash` in the manager; imported md5/SCRAM `pg_authid` verifiers are re-hashed on first sign-in; `access_grant` is the instance entry boundary; lock after the 4th failure, all audited to `admin_audit`. `database.js` `authenticate` *is* `authenticateIdentity`. A grant is enough to get in: the local `user_account` profile is made on first sign-in (B.7, `provisionProfile`). There is no `authStrategy` setting; if a config or doc mentions one it is stale.
- **Identity is scoped to an organization.** One username in two organizations is two people with two passwords. `test/api/isolation.test.js` proves it (F.1), including by mutation.
- **Three admin tiers:** platform (`identity.is_platform_admin`), organization (`identity.is_org_admin`), instance (a tenant super user, `user_account.is_super`, limited to the instance they are signed in to). No tier gets 401.
- **Membership** is a recursive CTE over `role`/`role_membership` (`tools.memberNames`), not `pg_has_role`.
- **User management never touches the cluster.** `server/services/role.js` keeps the trigger-facing names (`createRole`, `dropRole`, `changeRoleLogin`, `changeRolePassword`) but writes identities and grants; `changeRoleCreateDb`/`grantMembership`/`revokeMembership` are gone. `Role.isLogin` stays as the user-vs-group discriminator. `scripts/services.js` is the *installed* core-services script, so a change to the Role/UserAccount triggers needs `node install.js --instance <name>` on every instance (and on `demo` before running the suite, which clones it). The UserAccount before-trigger asks `isAuthorized` before writing a password: trigger side effects run before `crud` refuses the update.
- **The lifecycle is on screen (D.1/D.4).** Platform administrators create an instance from a template (resumable "$provision" state machine in the manager, FOR UPDATE SKIP LOCKED per step, Resume on the row), drop one, and copy a quiet instance into a template (service-account build; only the pg_database mark needs a superuser and it is best effort). Registering checks the `"$db"` marker; a closed instance refuses sign-in; expired demos (`isDemo` + past `expiration`) are closed hourly by the server's sweep, audited, never dropped. A registered instance is never a quiet clone source while a server serves it -- createDatabase releases its own pool first; anyone else's connections still refuse.
- **Passkeys and the second factor are the identity's and the organization's (C.1/C.2/E.2).** Credentials in manager table `"$identity_credential"` (grant-joined lookup: a passkey goes exactly where its identity can), single-use expiring challenges in `"$identity_challenge"`, signature counter enforced, registration audited; `migrate-identities.js` copies old per-instance rows. `organization.isTwoFactorRequired` decides the envelope per organization; config `twoFactorAuth` stays as the global override.
- **Multi-node (E):** `f.datasource.claimWork(key, seconds)` is the once-across-nodes primitive ("$claim" in the manager) the CronJob module is to call; sessions are `resave: false`; tenant pools capped by `pgTenantPoolSize` with `pgTenantIdleTimeout`, budget documented in the README. `test/api/multinode.test.js` runs two servers and proves shared sessions, cross-node challenges, the provisioning claim and one-winner claims.
- **Two screens, both inside an instance,** in the Home tab's Global group: **Users** (`#!/admin`, `client/components/admin-page.js`) for identities, grants, status and the audit trail; **Instances** (`#!/instances`, `client/components/admin-instances-page.js`) for the registry -- register a database that exists, attach one that belongs to no organization, open or close sign-in. Both served by `server/services/admin.js` over `/:db/admin/...`. Neither is in `client/clientmin.js`, so both need `"debug": true`.
- **Install and migration.** `node install.js --instance <name> [--organization X]` is identity-native: finds or creates the organization (keeps the one an instance already has), attaches, makes the service account (`pgUser`/`pgPassword`) an identity with a grant, org admin, and platform admin if it is the first identity anywhere; idempotent; unknown flags are fatal (they used to reinstall the manager silently). The old identity backfill (`scripts/migrate-identities.js`) was removed 2026-10-22 because every installation in use has been moved; it survives at tag `v3.0.0-alpha.1`. Self upgrade at startup is two booleans, `selfUpgradeManager` and `selfUpgradeInstances`: each compares Core versions and runs `install.js --manager` / `--instance <name>` for the manager and every registered instance that is behind. Until it has run nobody can sign in.

Open questions from the ADR that are still open: HA topology for the manager, session strategy (E.3), a per-tenant `everyone` equivalent, service accounts and API tokens, org-scoped email flows.

### Packages on disk: where it landed (ADR 002)

Module code and feather definitions live in versioned packages on the server's file system; a database records which versions are deployed into it. As of 2026-10-16 the ADR's implementation is done except for what section 10 of the ADR lists as open.

- **Install and Deploy are two acts.** `node install.js --package <dir|tarball>` registers a package at `modules/<module>/<version>/` and touches no database (its libraries are installed in its own version directory); `--packages` lists what the server holds; `node install.js --deploy <module>[@version] --instance <db>` (or `--manager`) holds the instance, applies the manifest, records the version in that database's `module` row and lets it go. **A failed deployment leaves the instance held on purpose.** `install.js` exits non-zero on failure now.
- **Maintenance is a state on the registry row** (`Tenant.isMaintenance`, ADR-002 q7). A held instance answers 503 with an explanation for everything but its own pages, sign-in and `/:db/admin/...`, and only a platform administrator can sign in -- on a one-instance installation the screen that ends it is served from that instance. Both ends audited. Reads probe for the column, so an un-upgraded manager reports nothing held; **`node install.js --manager` adds it.**
- **The fleet view** is the Instances screen's Modules column: what each instance carries (read from the instance, not from the registry's cached `Tenant.modules`), how many modules are behind a package the server holds, and "Deploy" on the row. Upgrading many instances is a rolling outage, so the screen counts and a person chooses the order.
- **Both halves of "source code in a table" now come from disk.** Server services already did; a module's **client** script does too, for the version that database deployed, with the row as the fallback. Internal callers (isSuperUser) still see the rows.
- **`ModuleNpm` is retired** (q1): libraries are declared in the module's own `package.json` (`featherbone.libraries`, or every dependency camel-cased) and loaded from its own directory before its code runs. The rows are still honored for a module with no package and are read from the instance now -- the one-mode collapse had left that loader reading the manager.
- **A service row belonging to no module** is not loaded (it never was) and each database is told once, by name (q6). Nothing is deleted.
- Version comparison lives in the packages service (dotted numbers, prerelease before release) rather than a semver dependency; ranges would be the reason to add one.
- **Not built:** the Admin Console's combined zip install still installs *and* deploys (retiring it is a decision), a fleet upgrade as one action, and section 7's customer-extension tiers -- where improvement item 0.14 (column-level authorization) still gates spare user columns. Feather authorization editing in the Develop workbook is not needed yet: feather editing has not left the UI, so authorizations are still edited on the Feather form.
